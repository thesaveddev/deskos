**Current execution gate:** M4 is still in progress. The working Windows path covers attended consent, screen/control, multi-display capture, reconnect foundations, session diagnostics, the split `control`/unreliable `input` transport, a persistent browser-owned session runtime that keeps the WebRTC peer alive across ReyDesk route changes, endpoint presence, permission-gated text clipboard synchronization, an audited elevated terminal channel (commands execute immediately over the ordered channel), a confined chunked file manager rooted at the managed public-files directory with the endpoint root surfaced in the console, and elevated process/service inventory with protected service actions. Elevated capabilities now use a two-stage endpoint consent: the base session prompt plus an explicit elevated-access warning, and declining elevation continues the session with screen/input only while recording `session.elevation_denied` in the timeline. Session chat is persisted and audited, flows technician→endpoint over the broker relay, and supports technician invite (owner/technician/observer roles) and ownership transfer with tenant-membership checks. Session lifecycle, consent, chat, and collaboration events mirror into the linked ticket's thread as `session_record` entries. Endpoint chat reply and on-screen display are delivered: the service writes technician chat into a shared per-session mailbox (`%ProgramData%\ReyDesk\chat`), and the logged-in-user tray helper opens a lightweight browser chat page on the first new message so the endpoint user can read and reply; replies are persisted and audited via the API and relayed back to the technician console in real time, and the mailbox is cleared on session end. Recording policy is now on the control plane: `remote_sessions` carries `recording_mode` (`off`/`metadata`/`video`, default `metadata`) and `recording_retention_days` (default 30), the session-create endpoint accepts and validates both, and an agent `POST /agent/sessions/:id/recording` lifecycle endpoint records `session.recording.started/stopped/failed` events while rejecting recording events after the session ends. Video recording capture is delivered end-to-end: when `recording_mode` is `video`, the technician console records the consented WebRTC stream with MediaRecorder and uploads it via `POST /sessions/:id/recordings` into the tenant-scoped, RLS-protected `session_recordings` table (stored under `config.recordingDir`, size-limited), `GET /sessions/:id/recordings` lists them, downloads are auth-gated, and expired recordings are purged lazily according to `recording_retention_days`. The two-relay Redis failover harness is delivered (cross-instance chat/SDP forwarding and room-registry survival across an instance close), and a repeatable broker churn/load harness (`apps/relay/load/harness.ts`) covers join ramp, message churn with exact delivery counts, reconnect storms, rate-limit enforcement, and graceful drain. A live local run against Redis passed the 500-connection / 50-session target and the 1,000-connection / 100-session headroom target (p95 join latency ~3 ms, 100% delivery, rate limit enforced). The remaining NAT/media half — direct P2P vs TURN fallback, packet loss, multi-monitor, reconnect after reboot — requires two coturn nodes. The unmanaged (ad-hoc) support flow is started on the control plane: a technician with `remote.attended` generates a 10–12 digit code and connect link (`POST /api/v1/adhoc-sessions`), the code is stored only as a sha256 hash behind RLS, a public `GET /connect/:code` reveals open-session metadata, and a single-use `POST /connect/:code/claim` mints an ephemeral device plus a `consent_pending` attended session and returns a device token with the relay URL (expired codes → 404, claimed-code reuse → 409). Technicians can also email either the numeric code or a high-entropy one-time link; link claims require a client fingerprint and bind the first helper, preventing replay from another client. The Sessions page now has a "Generate support code" panel showing the code, link, expiry, and permission toggles, and a public `/connect/:code` page renders the support request, the human-readable permission list, and the copyable code for the endpoint user (no auth). The portable helper is implemented as the agent's `helper` subcommand: `deskos-agent.exe helper <code>` redeems the single-use code (`POST /connect/:code/claim`), saves helper credentials, and runs the same consent + relay + screen/control loop as the installed agent with no installation; endpoints resolve from an explicit flag → a build-time baked default (`DESKOS_API_URL`/`DESKOS_RELAY_URL`) → the fleet registry → localhost. The connect page now offers a "Download the ReyDesk helper" button (rendered only when `GET /connect/:code` reports the helper is actually available) backed by `GET /api/connect/:code/download`, which streams the baked-endpoint helper binary (`DESKOS_HELPER_BINARY`, defaulting to `artifacts/windows/deskos-helper.exe`). The helper accepts the code on the command line or, when launched with no code (a bare double-click), opens a small native **ReyDesk support** window for the code — no terminal or browser. The agent's screen capture now uses the maintained `xcap` crate in place of the deprecated `screenshots`, which resolved the duplicate `windows` crate versions and unblocked the native dialog. Technicians can also list and revoke open support codes (`GET /api/v1/adhoc-sessions`, `POST /api/v1/adhoc-sessions/:id/revoke`, both `remote.attended`-gated and tenant-scoped via RLS; the plaintext code is shown only once and stored only as a hash, so the list shows metadata and state). The technician-side handoff is complete: claim creates the issuing technician's `session_participants` owner row plus a `session.created` event and notifies the technician, and the support-code panel auto-refreshes to surface a one-click **Open live session** deep-link with the session's live state the moment the code is claimed — so the technician no longer has to hunt for the session in the list. The only remaining gap for the AnyDesk-style journey is release signing (code-signing certificate, update manifests, and a SmartScreen-friendly distribution). Redis broker work is production foundation only; it does not move the project past the M4 exit criteria.

The `notify()` pipeline now consults the user's per-kind preference and either suppresses delivery (`enabled=false` or empty `channels`) or records the requested channels (`in_app`/`email`) on each notification; absent a preference the default is enabled + `in_app`. Self-service routes (`/api/v1/notification-preferences`, any authenticated tenant member) list a canonical set of kinds with current state, upsert per-kind `enabled`/`channels`, and delete to reset. Web Settings gains a **Notifications** tab with a per-kind mute toggle and in-app channel control. Production-readiness work is now active: API and relay readiness probes, Prometheus-compatible relay metrics, connection/session/message guardrails, configurable database pool sizing, stale-frame dropping, low-frequency input-audit backpressure, and a Redis-backed room/ticket/pub-sub adapter are implemented. The relay readiness probe intentionally fails in production until Redis is configured and live failover/load tests pass; the no-Redis mode remains suitable only for development or a single non-HA instance. Remote-plane security coverage now includes a relay ticket module with unit tests (signing, tamper/expiry/audience rejection, and single-use consumption), a live WebSocket integration suite (join-ticket reuse, tamper rejection, chat forwarding, and `session_end` authorization), and API tests for consent replay, invalid agent state transitions, and post-end audit rejection. The relay was refactored into an instance-scoped `createRelayRuntime` factory (with `buildRelayApp` kept for compatibility), so multiple relay instances can share Redis in one process, and now runs 17 tests. A two-relay failover/rolling-restart harness verifies cross-instance SDP/chat forwarding and room-registry survival when one relay instance stops. Redis room membership now uses a heartbeat-refreshed sorted set with a configurable TTL (`RELAY_MEMBER_TTL_MS`, default 60s; `RELAY_MEMBER_HEARTBEAT_MS`, default 15s): each relay refreshes its own peers' scores, and stale members are swept before capacity counting so a crashed peer or relay can no longer wedge a session at capacity. The relay runs 18 tests, and the broker churn/load harness passes 500/50 and 1,000/100 locally. Short-lived coturn REST-API TURN credentials are now minted by the API (`GET /sessions/:id/ice` for technicians and `GET /agent/sessions/:id/ice` for the agent, both returning `{ iceServers }`), consumed by the browser runtime and the Rust agent at session join, and a local coturn service is defined in `docker-compose.yml`; the default is STUN-only, and TURN activates via `DESKOS_ICE_TURN_*` (`DESKOS_ICE_TURN_SECRET` is the coturn `static-auth-secret`). W3C trace-context propagation is delivered: the API honours inbound `traceparent` and always emits its own plus `x-trace-id`, so requests can join a distributed trace; and a synthetic attended-session probe (`POST /api/v1/probe/attended-session`) exercises the real device → session → participant → signed join-token path inside a rollback transaction and records `deskos_synthetic_probe_checks_total{check="attended_session"}` without polluting tenant data. The agent update channel is delivered on the control plane: `GET /api/v1/agent/update` offers a configurable release (`DESKOS_UPDATE_VERSION/URL/SHA256/SIGNATURE/ROLLOUT_PERCENT`) behind a deterministic per-device rollout ring, and `POST /api/v1/agent/update/telemetry` records audited `agent.update.*` events; the agent checks on a slower cadence than heartbeats and reports availability, with a `check-update` subcommand for manual testing. A `verify-update` subcommand enforces SHA-256 and, when `DESKOS_UPDATE_PUBLIC_KEY` is baked at build time, ed25519 verification of a downloaded artifact against `<version>:<sha256>`. Remaining delivery work: download + apply with rollback health checks, then code signing. Observability is delivered end-to-end: Prometheus metrics, W3C traceparent propagation, the OTLP/HTTP JSON trace exporter, the synthetic attended-session probe, and optional Sentry error capture gated on `DESKOS_SENTRY_DSN`. The API, relay, and web were upgraded for security (Fastify 5 with `@fastify/*` v11-13, React Router 7, Vite 6, Vitest 3) and `npm audit` now reports zero vulnerabilities. Remaining trust-boundary work: the WebRTC NAT/media lab (direct-vs-TURN measurement, packet loss, multi-monitor) once coturn nodes are provisioned.

**Exit:** full MVP checklist in `02-prd.md §5` satisfied; load test: 500 concurrent WS + 50 sessions stable with headroom exercised at 1,000–2,000 WS / 100–150 sessions; a11y AA audit clean on core flows; Redis-backed broker registry/pub-sub, two redundant relay/TURN nodes with TURN over UDP + TCP/TLS 443, peer-to-peer-first ICE with measured direct vs TURN-fallback rates, signed agent releases, object storage, tracing, and a repeatable k6/Playwright load/NAT lab are required before production claims. Production infrastructure follows the staged deployment blueprint in `04-system-architecture.md` §5 — one application VPS with Redis/PostgreSQL co-located and no dedicated load balancer, plus two relay/TURN nodes; do not provision Kubernetes, read replicas, Redis Cluster, or regional TURN until metrics justify them.

**Script library ✅ DONE:** `scripts` (tenant-scoped, RLS) hold versioned, approval-gated script bodies (name, category, `os[]`, `version`, `body`, `args_schema`, `privilege_level` user/elevated, author + approver), and `script_runs` (tenant-scoped, RLS) record each execution with args, exit code, output reference, actor, and optional device/session. **Endpoint monitoring rules ✅ DONE:** migrations `0022_monitoring_rules.sql`, `0053_monitoring_health_rules.sql`, and `0054_monitoring_operations.sql` now provide a tenant-scoped, RLS-enforced monitoring suite. Rules cover CPU, memory, disk, battery level/health, network latency, uptime, process count, heartbeat age, and service state, with device-type and device-group scope, sustained-duration windows, business-hours and maintenance suppression, alert-only or ticket actions, team routing, escalation levels, and message templates. Eight existing monitoring tests plus new lifecycle, suppression, heartbeat, overview, and availability coverage protect the behavior. More advanced local service collectors and predictive anomaly models remain future enhancements rather than being presented as complete.

### AI ticket triage ✅ IMPLEMENTED

ReyDesk now supports tenant-controlled, bounded Level-1 ticket triage for portal, email, and phone-originated requests. When AI is configured and enabled, a new requester ticket is evaluated asynchronously; the assistant can ask one safe diagnostic question at a time, persist the public response as an `ai_triage` thread, deliver the same response through the branded email queue, and resume when the requester replies. A high-confidence resolution can close the ticket only when the tenant policy allows it; otherwise the assistant requests confirmation or hands the ticket to a technician. Risky, ambiguous, secret-seeking, malformed, provider-failing, and over-limit flows are handed off or disabled without executing endpoint actions. Technicians can inspect state, retry, or stop triage from the ticket, and all triage replies, confidence, rounds, and handoffs are auditable in the ticket timeline. Settings are available under **Settings → AI ticket triage** (`enabled`, public replies, auto-resolution, maximum rounds, confidence floor, and source scope). The provider remains OpenAI-compatible and injectable for tests; AI is never part of the ticket creation critical path.

## Go-live stage — remaining release gates

The ordinary application modules are substantially complete. The remaining blueprint work belongs to the **Go-live stage** and is required before ReyDesk should be marketed as production-ready. These are release, infrastructure, reliability, and distribution gates rather than new ordinary UI modules:

1. **Agent update download/apply with rollback health checks** — the signed update manifest, download, hash/signature verification, and rollout metadata exist; the Windows agent still needs safe in-place apply, restart health checks, rollback, and audited failure recovery.
2. **Signed Windows agent/helper releases and SmartScreen distribution** — obtain and protect an Authenticode certificate, sign the MSI and portable helper, publish signed hashes/manifests, and verify SmartScreen-friendly installation and update flows.
3. **Production coturn deployment and NAT/media testing** — provision TURN nodes with UDP plus TCP/TLS 443 fallback and measure direct-vs-TURN success, packet loss, ICE failures, multi-monitor capture, reconnect, and bandwidth behaviour.
4. **Object storage for recordings and large attachments** — move durable recordings, attachments, exports, diagnostic bundles, and release artifacts from local disk to S3-compatible storage with signed URLs, lifecycle retention, quotas, and restore testing.
5. **Durable webhook retry queue and replay protection** — move delivery attempts to a durable worker queue, add exponential backoff/dead-letter handling, idempotency keys, replay windows, and outbound destination controls.
6. **Repeatable k6/Playwright production load tests** — exercise the API, ticket queues, telemetry ingestion, relay churn, 500 WebSocket/50-session targets, and headroom scenarios around 1,000–2,000 WebSockets/100–150 sessions.
7. **Multi-node relay/TURN deployment** — deploy at least two redundant relay/TURN nodes, Redis-backed ownership and failover, graceful draining, alerting, and synthetic attended-session probes.
8. **Android/iOS release packaging** — the Android endpoint agent source ships in `apps/agent-android/`; remaining work is CI signing for release APKs, FCM/APNs wake pushes so consent requests reach closed apps, and device-farm testing of remote support, lock behaviour, and notifications.
9. **On-device execution for approved scripts** — complete agent-side retrieval, signature/policy validation, execution, output capture, cancellation, timeout, rollback/cleanup, and end-to-end audit correlation for the already approval-gated script library.

The working tree also contains earlier uncommitted changes from this thread, including generated local logs and recording artifacts. Those are development artifacts, not release deliverables; they must be reviewed, excluded from the release commit, or deliberately migrated before go-live.
